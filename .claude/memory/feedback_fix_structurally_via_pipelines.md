For infrastructure and deployment problems, drive the fix through the fleet's structural machinery — gyrum-catalog manifests, warp tickets, `gyrum-fire-playbook`, and the dark-factory ansible roles — not manual hand-edits on hosts.

**Why:** Jon: "i want all this sorted structurally probably via the pipelines." A hand-fix on a host bypasses every gate and drifts from the declared source of truth (the manifest). During the warp#10929 cockpit fire, the drag came from registry drift (warp-02's tunnel was hand-onboarded and never entered into the peer registry) — the pipeline did the right thing given its inputs, but the inputs had drifted. The fix was to reconcile the registry and harden the tooling (gyrum-wg-config now adopts an existing vault keypair instead of minting a wrong key), not to keep hand-managing peers.

**How to apply:**
- Correct the manifest / ansible role / pipeline, file or claim the warp ticket, fire via `gyrum-fire-playbook` (or auto_deploy), then verify the deployed result live.
- Manual server-side steps (SSH, hand-editing config) are for READ-ONLY diagnosis only — never the fix itself.
- When a tool's assumption drifts from reality (e.g. a peer exists on the host but not the registry), fix the TOOL structurally (reconcile + harden) rather than working around it by hand.
- These seeded memories are GENERATED by seed-claude-memory.sh (gyrum-labs/devtools) — the seed script is the source of truth. To change a seeded memory, edit seed-claude-memory.sh and re-run gyrum-seed-claude-memory; never hand-edit the generated file under ~/.claude/projects/<proj>/memory/ (the next seed run overwrites it). Updating a memory is itself a structural change, not a direct edit.
